## 2. Conventions

| Topic | Rule | Why |
|-------|------|-----|
| Primary keys | `UUID` for entities that appear in API URLs; `BIGINT` identity for append-only logs and the skills lookup. **[A] DD-01** | Sequential ids in URLs invite guessing (`/applications/41`, `/42`). Authorization is still the real protection, but unguessable ids add depth. Logs are never in URLs and are naturally ordered by id. |
| Id generation | UUIDs are generated by the application (version 4 in the MVP). | Simple. A time-ordered UUID can be adopted later if index locality becomes a measured problem. |
| Names | `snake_case`, plural table names. | Common PostgreSQL convention. |
| Timestamps | `TIMESTAMPTZ`, stored in UTC. `created_at`, `updated_at` on mutable tables. | Avoids time-zone bugs. Satisfies "add createdAt and updatedAt auditing". |
| Optimistic locking | `version BIGINT` on mutable tables where concurrent edits are plausible. | NFR-018: two recruiters changing one application must not silently overwrite each other. |
| Enumerations | `VARCHAR` + `CHECK (col IN (...))`. **[A] DD-05** | Readable in the database, easy to extend with a migration, no fragile numeric ordinals, no PostgreSQL ENUM migration pain. |
| Email | Stored lowercase, `UNIQUE`, plus a `CHECK (email = lower(email))`. **[A] DD-12** | Case-insensitive uniqueness without an extension. The application lowercases on input. |
| Text lengths | Bounded `VARCHAR(n)` for short text, `TEXT` for free text. | Defends against absurd input; the API validates the same limits. |
| Money, salary | Not modelled. | Not in the requirements. |

### 3.6 `applications`

| Column | Type | Rules | Notes |
|--------|------|-------|-------|
| `id` | UUID | PK | |
| `job_id` | UUID | NN, FK → `jobs` **RESTRICT** | D-16: the database itself refuses to delete a job that has applications. |
| `candidate_id` | UUID | NN, FK → `candidate_profiles` RESTRICT | |
| `resume_id` | UUID | **NN**, FK → `resumes` RESTRICT | D-15: a resume is mandatory. D-21: a used resume is never physically deleted. |
| `status` | VARCHAR(12) | NN, default `APPLIED`, CHECK in `APPLIED`,`SHORTLISTED`,`INTERVIEW`,`OFFER`,`ACCEPTED`,`DECLINED`,`REJECTED` | D-10, D-14. **Current** status; the full story is in the history table. |
| `created_at`, `updated_at`, `version` | | NN | `created_at` is the application date. |
| | | **UNIQUE (`job_id`, `candidate_id`)** | FR-032 AC3: no duplicate applications. |
| | | **FOREIGN KEY (`resume_id`, `candidate_id`) → `resumes` (`id`, `candidate_id`)** | FR-032 AC6: the resume must belong to the applicant. See DD-07. |

**Composite foreign key, in plain words:** `resumes` declares `UNIQUE (id, candidate_id)`, and `applications` points its pair (`resume_id`, `candidate_id`) at that pair. The database therefore accepts an application only if the resume really belongs to the same candidate who applies. Both columns are `NOT NULL`, which matters: PostgreSQL's default `MATCH SIMPLE` **skips** a composite foreign key when any of its columns is NULL, so a nullable column would silently disable the check.

### 3.8 `application_status_history` (append-only)

| Column | Type | Rules | Notes |
|--------|------|-------|-------|
| `id` | BIGINT | PK, identity | Ordered; never exposed in URLs. |
| `application_id` | UUID | NN, FK → `applications` RESTRICT | |
| `from_status` | VARCHAR(12) | NULL | Null only for the first row (creation). |
| `to_status` | VARCHAR(12) | NN, CHECK valid status | |
| `changed_by_user_id` | UUID | NN, FK → `users` RESTRICT | A recruiter, or the candidate for `ACCEPTED`/`DECLINED` and for applying. |
| `reason` | TEXT | NULL | **Internal, never shown to candidates** (D-27). |
| `created_at` | TIMESTAMPTZ | NN, default now | |

**Each history row records** (owner requirement):

| Required | Column |
|----------|--------|
| Actor | `changed_by_user_id` |
| Timestamp | `created_at` |
| Previous status | `from_status` (null only for the creation row) |
| New status | `to_status` |
| Reason (mandatory for rejection and for reopening) | `reason` |

The rule "a reason is mandatory when rejecting or reopening" (D-11, D-25) as a null-safe safety net:

```sql
-- sketch, not a migration
CHECK ( (to_status <> 'REJECTED' AND COALESCE(from_status, '') <> 'REJECTED')
        OR (reason IS NOT NULL AND btrim(reason) <> '') )
```

**Reopen** looks up the latest row where `to_status = 'REJECTED'` and returns the application to that row's `from_status` (D-11).
Each application has at least one row, so the relationship is "one or many".

### 3.10 `skills`, `job_skills`, `candidate_skills`

| Table | Columns | Rules |
|-------|---------|-------|
| `skills` | `id` BIGINT identity PK; `name` VARCHAR(60) NN | **Unique on `lower(name)`**, so "Java", "java" and "JAVA" are one skill. |
| `job_skills` | `job_id` UUID FK → `jobs` **CASCADE**; `skill_id` BIGINT FK → `skills` RESTRICT | **PK (`job_id`, `skill_id`)**: a job lists a skill once. |
| `candidate_skills` | `candidate_id` UUID FK → `candidate_profiles` **CASCADE**; `skill_id` BIGINT FK → `skills` RESTRICT | **PK (`candidate_id`, `skill_id`)** |

Why `CASCADE` here but `RESTRICT` elsewhere: deleting a job that has no applications (FR-052) should also remove its skill links; these rows are only a list, not history.

## 5. Constraints

### 5.1 Enforced by the database

| Rule | Mechanism | From |
|------|-----------|------|
| Unique email, lowercase | UNIQUE + CHECK on `users.email` | FR-001 AC3 |
| One role per account, valid role | single column + CHECK | Section 2 of requirements |
| One profile per user | UNIQUE `user_id` | |
| No duplicate application | UNIQUE (`job_id`, `candidate_id`) | FR-032 AC3 |
| A resume is mandatory to apply | `applications.resume_id` NOT NULL | D-15 |
| The resume belongs to the applicant | composite FK (`resume_id`, `candidate_id`) | FR-032 AC6, DD-07 |
| A job with applications cannot be deleted | FK `ON DELETE RESTRICT` | D-16 |
| A used resume is not physically deleted | FK `ON DELETE RESTRICT` | D-21 |
| Valid statuses, roles, job states, employment types | CHECK constraints | D-10, D-14 |
| Resume size 1 byte to 5 MB | CHECK on `size_bytes` | D-09 |
| Reason mandatory when rejecting or reopening | CHECK on history | D-11, D-25 |
| Phone optional; name and email mandatory | nullability | D-13 |
| `closed_at` set exactly when a job is closed | CHECK | D-03 |
| No resume URL stored | only `storage_key` exists | D-17 |

### 5.2 Enforced in the service layer (the database cannot express them well)

| Rule | From |
|------|------|
| Allowed status transitions, forward only, no skipping | D-10, FR-035 |
| Who may make each transition (recruiter vs candidate) | D-18, section 3.1 of the stories |
| Reopen only by the owning recruiter, only when the job is open, back to the previous status | D-11, D-20, D-23 |
| Apply only to open jobs; closed jobs keep their pipeline running | D-26 |
| At most 5 active resumes; PDF content check; unused resumes physically deleted | D-09, FR-040, FR-042 |
| Admins cannot read applicants or resumes | D-24, D-28 |
| A recruiter cannot post a job before a company exists | FR-020 AC2 (partly also `jobs.company_id` NOT NULL) |
| History and audit rows are only ever inserted | D-12 (no update/delete code path; optionally a database permission or trigger later) |
| Status history row is written in the **same transaction** as the status change | NFR-018 |

**Decision – constraints in both places:** the service layer gives users friendly errors; the database is the last line of
defence against bugs and against scripts that bypass the service. Complex workflow logic stays in the service layer (NFR-023),
where it can be unit-tested.

## 6. Indexes

An index speeds up reads for one query shape and slows down writes a little, so each one is tied to a real query. Primary
keys, UNIQUE constraints and primary-key prefixes are indexed automatically. **PostgreSQL does not index foreign keys
automatically**, so the ones used for joins are listed explicitly. These are initial; Phase 8 measures and adjusts them.

| Index | Serves | Source |
|-------|--------|--------|
| `users(email)` (the unique one) | Login lookup | FR-002 |
| `jobs(created_at DESC) WHERE status = 'OPEN'` (**partial**) | Public job list, newest first, without indexing closed jobs | FR-031 |
| `jobs(company_id)` | A recruiter's own jobs; FK join | FR-030 |
| `jobs(employment_type)`, `jobs(lower(location))` | Filters on the list | FR-031 AC1 |
| `applications(job_id, status)` (the unique `(job_id, candidate_id)` already covers `job_id` alone) | Recruiter lists applicants of a job, filtered by status | FR-034 |
| `applications(candidate_id, created_at DESC)` | "My applications" | FR-033 |
| `applications(resume_id)` | "Is this resume used?" (D-21) and FK checks | FR-042 |
| `resumes(candidate_id) WHERE hidden_at IS NULL` (**partial**) | Active resume list and the limit-of-5 count | FR-040, FR-042 |
| `application_status_history(application_id, created_at)` | Show an application's history; find the latest rejection | FR-033, FR-036 |
| `audit_log(entity_type, entity_id)`, `audit_log(created_at)` | Look up an entity's audit trail | NFR-039 |
| `job_skills(skill_id, job_id)` | "Jobs requiring skill X" | FR-031 AC1 |
| `candidate_skills(skill_id, candidate_id)` | Reverse lookup | Phase 7 |
| `recruiter_profiles(company_id)` | FK join | FR-020 |

**Honest limit:** keyword search in job titles and descriptions (`ILIKE '%word%'`) cannot use a normal B-tree index. That is
acceptable for a small MVP dataset and is replaced by Elasticsearch in Phase 8. I will not claim it is fast until it is measured (NFR-001).

## 7. Normalization review

| Normal form | Check | Result |
|-------------|-------|--------|
| **1NF** (atomic values, no repeating groups) | Skills could have been a comma-separated column. They are rows in `skills` plus junction tables instead. | Pass |
| **2NF** (no partial dependence on part of a composite key) | The junction tables have only their two key columns. `applications` has a single-column PK. | Pass |
| **3NF** (non-key columns depend only on the key) | Company data lives in `companies`, not repeated on every job. The user's name lives in `users`, not copied into profiles. | Pass |

**Deliberate, documented redundancy:**
- `applications.status` can be derived from the latest history row. It is kept because the "list applicants by status" query
  must be fast, and because the history table is the audit record, not the live state. Both are written in one transaction
  (see DD-06).
- `applications.candidate_id` is also reachable through `resume_id`. It is kept for the unique rule and for queries, and the
  composite foreign key makes it impossible for the two to disagree.
- `location` is free text rather than a `cities` table: the extra table adds complexity without a requirement (DD-15).

## 8. Transaction requirements

A status change touches two tables (`applications` and `application_status_history`). If only one write survived, the
current state and the audit trail would disagree. **Both writes must succeed or neither.**

### 8.1 Changing an application's status (FR-035, FR-036, FR-037)

One service method, one database transaction (`@Transactional` in Spring, Phase 1):

1. Load the application (it carries its `version`).
2. Check who the actor is and whether they may make this move (section 3.1 of the user stories).
3. Check the transition is allowed, the job state allows it (reopen needs an `OPEN` job, D-23), and a reason is present when rejecting or reopening.
4. For a reopen: read the latest `REJECTED` history row **inside the same transaction** to find the status to return to.
5. `UPDATE applications SET status = ?, version = version + 1, updated_at = ? WHERE id = ? AND version = ?`. If **zero rows** change, someone else got there first: roll back and answer HTTP 409 (the optimistic lock).
6. `INSERT` the history row: `from_status` (the old status), `to_status`, `changed_by_user_id`, `reason`, timestamp.
7. Commit. If anything in steps 5 or 6 fails, including the database CHECK on the reason, **everything is rolled back** and the status is unchanged.

Rules:
- The history `INSERT` is never done asynchronously, after commit, or in a separate transaction.
- Later events (Phase 6) are written to the **outbox table in this same transaction**, never published straight from the method.
- The default `READ COMMITTED` isolation plus the version check is enough. Contention is low (a few recruiters per job), so row locks (`SELECT ... FOR UPDATE`) are not needed.
- Read-only queries use read-only transactions.

### 8.2 Other multi-write operations

| Operation | Must be atomic |
|-----------|----------------|
| Apply for a job | Insert the application **and** its first history row (`from_status` NULL, `to_status` `APPLIED`, actor = candidate). A duplicate hits the unique constraint and answers 409. |
| Register a candidate | Insert `users` **and** `candidate_profiles`. |
| Create a company | Insert `companies` **and** set `recruiter_profiles.company_id`. |
| Admin deletes a job | Delete the job (its `job_skills` cascade) **and** insert the `audit_log` row. If the job has applications, the foreign key refuses the delete and nothing is written. |
| Hide or delete a resume | Check "is it used?" and act in one transaction. A concurrent application that references the resume is still caught by the foreign key. |

### 8.3 Tests Phase 1 must include

- A failing history insert leaves the status unchanged (same-transaction rollback).
- Two concurrent changes: exactly one succeeds, the other gets 409.
- A reopen returns to the status held before the latest rejection.
- A rejection or reopen without a reason is refused by the service **and** by the database.

## 9. MVP business rules vs future schema flexibility

A **business rule** says what the product allows today. **Schema flexibility** says what the tables could hold without a
migration. They are separate on purpose: a limit that may change should be a service rule, not a database constraint, and
we should never claim a capability exists just because the schema could store it.

| Topic | MVP rule (where enforced) | What the schema allows later | What a change would need |
|-------|---------------------------|------------------------------|--------------------------|
| Recruiters per company | **One.** Service layer. | Many (no `UNIQUE` on `recruiter_profiles.company_id`). | Requirement change, new service code and invitation flow. No migration. |
| Roles per user | **One.** Single `users.role` column. | One only. | A `user_roles` table and a migration (FUT-002). |
| Active resumes per candidate | **5.** Service layer. | Any number. | Config change. |
| Resume size | **5 MB.** Service check **and** a database `CHECK` (`size_bytes <= 5242880`). | Up to the CHECK value. | A migration to change the CHECK. Consider a looser database ceiling if the limit may grow. |
| Deleting a job | **Refused if it has applications.** Foreign key `RESTRICT`. | Same. | The retention policy (Q7) may add a soft-delete column. |
| Application statuses | **7 values**, forward-only workflow in the service layer. | Values limited by the `CHECK` list. | A migration to add a value (for example `WITHDRAWN`, FUT-001) plus service rules. |
| Who sees applicants and resumes | Recruiters of the owning company only. Admins cannot (D-24, D-28). Service and security layer. | Not a schema matter. | A new requirement and authorization rules. |
| Reasons visible to candidates | **No** (D-27). Candidate-facing DTOs omit `reason`. | `reason` is stored regardless. | A requirement change. |
| Account deletion | **Not offered.** All user foreign keys are `RESTRICT`. | Not supported. | A retention and anonymization policy (Q7). |
| Employment types | 4 values (`CHECK`). | | A migration to add one. |
| Services | One database (modular monolith). | Splittable by module. | Phase 5: cross-module foreign keys become plain ids. |

**Resume storage stays private:** the database stores only an opaque `storage_key`, never a URL or a public path. The bucket
name is configuration, access is through an authorized backend endpoint, and no schema element could be used to build a public
link (D-17).

## 10. Design decisions (approved)

| ID | Decision | Alternatives considered | Why this one |
|----|----------|-------------------------|--------------|
| **DD-01** [A] | UUID keys for API-visible entities; BIGINT identity for logs and `skills`. | UUID everywhere; BIGINT everywhere. | Unguessable ids in URLs; cheap ordered log tables. |
| **DD-02** [A] | One `users` table with a `role` column, plus one profile table per role. | One table per role; a single table with many nullable columns. | Login and authorization need one table; role-specific data stays out of it. |
| **DD-03** [A] | `recruiter_profiles(user_id, company_id)` links recruiter to company. | `company_id` column on `users`; `owner_user_id` on `companies`. | Keeps `users` role-neutral and supports several recruiters per company later with no schema change. The MVP business rule stays one recruiter per company (service layer, section 9). |
| **DD-04** [A] | Normalized `skills` with junction tables. | A comma-separated text column; a PostgreSQL `text[]` array with a GIN index. | Skill filtering (FR-031), consistent names and the Phase 7 AI work all need skills as data. Cost: three extra tables. **Simpler alternative:** `text[]` + GIN index. |
| **DD-05** [A] | Enums as `VARCHAR` + `CHECK`. | PostgreSQL ENUM type; integer ordinals; lookup tables. | Readable, easy to migrate, safe. |
| **DD-06** [A] | Current status on `applications` plus a full history table, written in one transaction. | Only history; only current status. | Fast queries plus a complete audit trail (D-12). |
| **DD-07** [A] | Composite foreign key (`resume_id`, `candidate_id`) → `resumes(id, candidate_id)`. | Service-layer check only. | The database makes it impossible to attach someone else's resume. |
| **DD-08** [A] | `RESTRICT` on all history-bearing foreign keys; no soft-delete for jobs. | `CASCADE`; soft-delete flag on jobs. | D-16 means a job with applications can never be removed, so a deleted flag buys nothing yet. Revisit after the retention policy (Q7). |
| **DD-09** [A] | Resumes hidden with `hidden_at`; unused resumes physically deleted. | A boolean flag; always keep. | Matches D-21; the timestamp says when. Hidden resumes do not count toward the limit of 5 and a used resume is always retained (D-31); how long hidden files are kept stays open (Q7). |
| **DD-10** [A] | `audit_log` has no foreign key to the audited entity. | An FK with `SET NULL`. | The log must survive the deletion it records. |
| **DD-11** [A] | `TIMESTAMPTZ` in UTC; `version` columns for optimistic locking. | Local `TIMESTAMP`. | Standard, avoids time-zone bugs; NFR-018. |
| **DD-12** [A] | Lowercase email + UNIQUE + CHECK. | `citext` extension; unique index on `lower(email)` only. | No extension to manage in Docker, Testcontainers or Kubernetes. |
| **DD-13** [A] | `full_name` on `users`. | On `candidate_profiles`. | Recruiters and admins need a name too (FR-001). |
| **DD-14** [A] | Database `CHECK`s for valid values, the resume size and the mandatory reason; transition logic stays in the service layer. | Transition rules as a database trigger. | Safety net without hiding business rules in SQL (NFR-023). |
| **DD-15** [A] | Locations are free text. | A `cities` table. | No requirement needs more yet. |
